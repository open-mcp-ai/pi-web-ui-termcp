# 🖥️ termcp

把 [termcp](https://github.com/open-mcp-ai/termcp) 接进 pi-web-ui。

**这个插件只有两件事：**

1. **注入 MCP** —— 用 termcp 官方那条命令把它的 31 个工具交给 AI。
2. **开一个窗口** —— 把 termcp 的界面反代过来，嵌进顶栏看。

就这些。装上即用。

## 1. 注入 MCP

命令就是 [termcp.org](https://termcp.org) 给所有客户端的那一条，**无条件使用**：

```
npx -y @open-mcp-ai/termcp daemon stdio
```

交给宿主的 `host.mcp.install()`，它负责写配置、拉起进程、握手、把工具注册进会话。插件不实现 MCP、不写配置文件、不管进程生命周期。

`daemon stdio` 本身就是「确保实例存在」——在跑就接管，没在跑就拉起。所以不需要探测端口。

**已经配好就不动它。** 哪怕参数一模一样也不行 —— `install` 会重启服务器，把用户正在用的终端杀掉。参数变了才刷新。

**用户手写的配置绝不覆盖。** 宿主 `check()` 分不出「谁配的」，所以插件在自己那条上打了 `[plugin:termcp]` 标记；没有标记的一律不碰。

只有一处不那么显然的代码：**install 之前先预热**。宿主的 MCP 握手超时是硬编码的 8 秒（`server/mcp-bridge.ts` 的 `start(timeoutMs = 8000)`；配置里的 `timeout` 字段只被存进快照，没有任何一处读它），而 npx 首次要下载 ~12MB。实测不预热：

```
[mcp] 服务器「termcp」启动失败： initialize 超时 (8000ms) → 0 个工具
```

先跑一次 `-version` 等它落地就没这个问题了。装过之后这步是瞬间的。

## 2. 开窗口

把 `<prefix>` 反代到 termcp 的 HTTP 端口，用 iframe 铺满顶栏视图。

为什么是 iframe 而不是重写：termcp 的前端是一整套终端工作区（xterm 网格、会话窗口、标签页、端口转发对话框、审批队列）。重写就是维护第二份实现，而且一定会漂移。宿主的 `registerProxy` 就是为这个场景准备的——它转发 HTTP 和 WebSocket 升级（终端 I/O 走 WebSocket）。

状态栏只说一件事：AI 那边通没通。它不探测端口（那是宿主 MCP 桥的事，而且第二意见只会跟它打架），也**不报反代挂没挂上**：宿主 `registerProxy` 失败时返回的同样是「一个什么都不做的函数」，插件侧分辨不出成功与否，失败只进宿主的运行时诊断。谎报比不报更糟，所以没有这个字段。

> **一个已知的宿主时序坑**：同前缀的插件升级时（旧插件目录删掉、新插件顶上），宿主先 activate 新插件、后 deactivate 已删的旧插件，中间那一段 `<prefix>/` 会落到宿主的 SPA 兜底——用户在「termcp 窗口」里看到 pi-web-ui 自己。插件的对策很简单：**每次窗口问状态时重挂一次**（宿主按 pluginId 认领，对同一个 owner 是幂等的），所以打开窗口或点「重载」即自愈。
>
> 顺带一提，宿主那两处兜底清理（`releaseEntry` / `dispose`）都是**按 pluginId 过滤**的，不会扫掉别人的路由——所以自愈只需要覆盖「注册被拒 / 被自己人撤掉」这一小段窗口。

## 设置

只有三项。

| 项 | 默认 | 说明 |
| --- | --- | --- |
| `enabled` | `true` | 总开关。关掉 = 拆掉窗口反代 + 停用 MCP（进程收掉、工具从会话里消失）。 |
| `port` | `18765` | termcp 监听的本地端口。窗口的反代与 MCP 的 `--port` 都用它。 |
| `prefix` | `/termcp` | 窗口挂载路径，对应 `http://localhost:8787/termcp/`。 |

## 开关

**窗口工具栏上的「启用」勾选框**。关掉后反代拆掉、iframe 收起，状态栏提示去哪儿再打开。

它改的就是 MCP 面板里那个开关：**把 `termcp` 条目置为 `enabled: false`**（宿主 `reloadOnce` 会跳过停用的服务器，子进程被收掉、工具从会话里消失）。所以两个入口是同一个开关，不会出现「面板看着是开、实际却是关」。

行为对应用户的预期：

| 你做了什么 | 插件会怎么反应 |
| --- | --- |
| 在 MCP 面板里停用 termcp | **不碰它**，不会自作主张装回来 |
| 在窗口里关掉，然后去 MCP 面板把条目删了 | 不复活（删了就删了） |
| 改端口 / 挂载路径 | 开关不受影响（不会把刚关掉的默默打开） |
| 条目不存在（首次装） | 装上 |

**为什么不真删配置。** `host.mcp` 只给了 `list` / `check` / `install` / `promptInstall`，**没有删除 API**（删除在 `agent-service` 里，插件面看不到）。直接改 `~/.pi/agent/mcp.json` 需要 `fs` 权限 + 用户授权，也违背「插件不写配置文件」这条线。停用是插件能做到的最接近「卸载」的动作——效果就是 AI 拿不到工具了。

要**彻底删掉**那条配置，去设置 →「MCP」→ `termcp` 行右边的垃圾桶 🗑（那是宿主的界面，走得是真正的删除路径）。

开关只动**带 `[plugin:termcp]` 标记的自己的条目**：用户手写的 termcp 配置，关掉时也不会去停用它。

## 它对你机器的改动

- **一条反代**：`<prefix>` → `127.0.0.1:<port>`。反激活时撤销。
- **一条 MCP 配置**：`~/.pi/agent/mcp.json` 里的 `termcp` 条目（通过 `host.mcp.install` 写，不是插件直接改文件）。
- 不 spawn 进程（termcp 由宿主的 MCP 桥拉起）、不探测端口、不发 HTTP 请求。
- **反激活时不删那条 MCP 配置**——它是宿主的、也是设置面板里看得见的一条正常服务器。插件重载顺手杀掉连接和用户的终端是不对的。

## 前置条件

- **pi-web-ui ≥ 0.104.0**（`host.mcp` 从这一版开始有）。插件运行时检测这个接口，老宿主上会明确说「当前 pi-web-ui 没有 host.mcp」，只保留窗口。
  （不用 `manifest.engines` 门控：`readHostVersion()` 读的是 `<pkgRoot>/package.json`，而发布包里 `dist/` 下没有这个文件，回 `null` 后约束静默放行、不生效。运行时检测接口才靠谱。）
- **termcp 不用手动装。** 官方命令里 npx 会处理下载、缓存与升级。

## 自测

```bash
cd plugins/termcp
node selftest.mjs
```

75 项断言，一个假宿主，不需要 pi-web-ui、不需要 termcp、不联网。盯的就是那两件事：命令是不是官方那一条（PATH 上有 termcp、缓存里有二进制都**不影响**）、已配好时是否真的什么都不做、手写配置是否被放过；反代是否挂上、被占用后能否自愈、反复重挂会不会堆重复路由或漏副作用；开关的几种情形（面板停用不自作主张、关掉后删了不复活——含重载后、改端口不影响开关、窗口能开关）、以及关掉时会不会误伤用户手写的条目；反激活是否撤干净。

假宿主严格照抄真实宿主的两条语义（曾经因为写错而替一个真 bug 背书）：`registerProxy` 失败时返回的也是函数（不是 `null`），且同 pluginId 重复注册是幂等的。

## 卸载

卸载插件——反代会撤销。MCP 配置条目会留下（见上文），要清掉就在设置 →「MCP」里删掉 `termcp` 那条。termcp 自己的数据（`~/.termcp/`）不受影响。

想留着插件但只关掉功能，用上面那个 **启用 termcp** 开关；用 `pi-web-ui uninstall termcp` 则是把插件目录一并拿掉。
